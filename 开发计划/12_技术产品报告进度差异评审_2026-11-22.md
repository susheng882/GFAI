## 二、进度差异总览

| 维度 | 报告承诺 | 当前真实状态 | 判定 |

### 2.2 进度条（按报告主线 27 项口径粗算）

- 功能"存在性"：**约 22/27 项有接口或页面**（81%），缺口集中在账号注销/导出、套餐配额、供应商界面（V1.5）、自然语言问数（规划池）。
- 架构"符合性"：**约 3/8 条硬线符合**（T7 例外、状态机部分、三层目录部分）。
- 质量"可证明性"：**0/6 项质量指标有实测报告**（召回率/命中率/MRR/忠实度/拒答准确率/F1）。

> 这组数字说明：**当前进度是"功能做完了七成、架构对齐三成、质量证明零成"**。接下来不该再堆功能， priority 应从"做新东西"转向"补地基 + 补证据"。

## 四、设计上不适合 / 有问题的地方

> 这一节回答"哪里设计适合有问题"——不是功能缺失，而是**设计决策本身在当前约束下不合适**，需要主动纠偏。

### 4.1 架构层设计问题

**D1　报告架构与实现能力的"双轨制"没有收敛机制。**
代码里同时存在 `DEV_MODE` 的 SQLite/local 路径与生产 pgvector/MinIO 路径，配置默认值写的是生产、`.env` 实际跑的是 dev。后果：所有本地测试都在"假底座"上通过，生产栈首次实跑就是在服务器上。**建议**：把"生产栈冒烟"设为 G2 硬门禁（10 号计划阶段 A 已在做，必须真的执行），并让 `verify_all.py` 能在两种后端都跑一遍。

**D2　"单线程 worker + 看门狗"的设计_self-consistency 不足。**
看门狗杀超时任务、任务又被单线程队列串行阻塞——当队列积压时，排在后面的任务还没开始就被判定超时。Heartbeat 只解决"正在跑的长任务"，没解决"排队中的任务超时"。**建议**：任务态增加 `queued` 显式状态，看门狗只对 `running` 态计时，排队超时单独计。

**D3　三层幻觉治理的"分数阈值 0.7"从未真正生效。**
`config.py:54 RETRIEVAL_SCORE_THRESHOLD=0.7` 定义了但 `rag.py` 不使用；实际门槛是 `query_opt.RELEVANT_SCORE=3.0`（0–5 分域）与 `qa._MIN_COVERAGE=0.34`（覆盖率域），三套量纲各说各话。**建议**：统一为一个 0–1 置信度，BM25 分数归一化后与覆盖率融合，阈值单点可调、可被评测集校准。

**D4　成本护栏"三重"设计与真实成本量级不匹配。**
配额设 20000 token/日、成本上限 ¥250，而单次实际成本 ¥0.003 量级——护栏参数比真实消耗高 4–5 个数量级。**建议**：按产品报告真实单次成本（PDF ¥0.12、视频 ¥0.4）重设，并把 `config.py` 里那三个"摆设常量"与 `budget.py` 实际读取的变量对齐（见 S7）。

### 4.2 检索层设计问题

**D5　BM25 单路对"语义问法"先天无力，规则重排解决不了召回漏。**
`retrieve_multi` 已消除重复建索引（提速成功），但 `rerank_local` 只是"问题词覆盖率"打分——**它只能在已召回的块里排序，救不回根本没召回的语义相关块**。例如"怎么记住公式"召回不到讲"推导过程"的块。当前用"覆盖率不足 → 联网/模型知识兜底"掩盖，但这意味着**用户自己的资料在语义问法下经常答不到**，正好打中产品报告"把用户资料变成可召回上下文"的核心承诺。**这是问答质量的第一问题，必须靠向量路解决，不是调 prompt 能补的。**

**D6　`_chunk_stmt` 硬编码 `LIMIT 800`，数据增长后静默截断。**
800 块 × 300 字 ≈ 24 万字，一个重度用户几份 PDF 就到顶；超过部分不参与检索且不告警，与报告"禁止静默失败"冲突。**建议**：改为分页/增量索引或至少在达到 800 时告警提示"资料过多，检索仅覆盖最近内容"。

**D7　chunks 与 notes 两套检索路径未统一索引。**
`_recall_notes` 是后期补丁，与 chunks 各自为政，同一知识点可能命中其一而非最优，无法统一重排。报告的技术路线是"所有知识单元一个索引"。**建议**：把笔记正文切块后也写 `chunks` 表（带 `source_type` 区分 document/note），检索一次完成。

### 4.3 解析层设计问题

**D8　视频链路是"逐阶段串行 + 全片重扫"，没有体现三通道对齐。**
报告要求字幕轨/ASR/关键帧三路时间轴对齐到同一锚点。当前是线性流水线，OCR 虽已并发但仍是"抽完帧再逐帧传视觉模型"，没有网格拼图、没有字幕锚点。**建议**：短期加字幕优先取材（收益最大、改动最小）；中期用 `filter_complex` 一次解码抽多帧 + 拼图一次调用。

**D9　转写质量 `quality()` 标 low 但仍写 `ready`。**
`base` 模型中文错字（"间隔重复"→"建格重复"）直接进入卡片与问答，错误知识进复习闭环被反复强化——这是产品报告七（二）明确警告的"最伤信任的失败模式"。**建议**：low 质量不写 ready，触发"待确认队列"（报告的人在环校正设计），或至少在卡片上标"低置信"。

### 4.4 体验 / 联动层设计问题

**D10　仪表盘与学习计划未打通、计划页被移出导航。**
接口在（`/plans`），入口没了，完成度不进 stats，"今日该学什么"没有真正的决策代劳。报告把"今日任务卡"列为 P0 主线。**建议**：v3 指挥台的"今日待办"直接读 PlanTask.due + 复习 due，合并成一个队列。

**D11　问答策略切换靠 `_REFUSAL` 字符串匹配。**
`qa.py:510,529` 用回答里是否含"未在资料中找到依据"判断转联网——脆弱、不可解释、容易出现"该联网没联网"。**建议**：改成结构化置信度字段（`confidence` + `strategy` 由 `_kb_relevant` 直接返回），前端展示也用这个字段。

**D12　单文件 2849 行，技术债随时间线性增长。**
09 号评审时 2010 行，现在 2849 行——每次 UX 改动都往同一文件堆。已加 11 号的设计 token 化缓解了样式问题，但结构问题仍在。**建议**：按页面拆 module（至少把 QA、Dashboard、Notes、Quiz 四块拆出），这是"可维护"的最低要求，也是报告"分层"在前端的落点。

## 五、解析与问答：质量与速度优化

> 原则：**先修质量再修速度，但两者共用同一批改动**。很多提速手段（缓存、并发、本地小模型）同时提升稳定性；而"降模型换速度"必须以评测集验证质量不退化 >3pp 为前提（技术报告五（二）硬规则）。

### 5.1 问答质量优化（优先级从高到低）

| 优先级 | 动作 | 解决什么 | 落地方式 | 质量验收 |
|---|---|---|---|---|
| Q1 | **加本地向量召回路**（sqlite-vec / pgvector + bge-small-zh-v1.5） | D5：语义问法召回不到自己的资料 | 与 BM25 双路 → 按 chunk_id 去重合并 → 统一重排；这正是技术报告表 5 的设计 | 评测集召回率、命中率、MRR 逐版不降 >3pp |
| Q2 | **补实体一致性校验（第三层幻觉治理）** | S3：模型编造数值/专有名词无拦截 | 从答案抽数字/专名 → 与所引 chunk 比对 → 不一致标"存疑"或拒答，留痕 `不一致实体` 字段 | 拒答准确率、答案忠实度抽检 |
| Q3 | **统一置信度量纲**（0–1 单阈值） | D3：三套分数口径混乱 | BM25 归一化 + 覆盖率 + 向量相似度融合为一个 confidence，`RETRIEVAL_SCORE_THRESHOLD` 单点可调 | 阈值由评测集校准，不再拍脑袋 0.7 |
| Q4 | **chunks + notes 统一索引** | D7：两套路径无法统一重排 | 笔记切块写 chunks，加 `source_type` | 同一知识点只命中一个最优块 |
| Q5 | **本地交叉编码器重排**（bge-reranker-base） | 规则重排语义弱、LLM 重排慢且贵 | 替代 `rerank_local` 与 LLM `rerank`，CPU 可跑，无网络往返 | 命中率/MRR 不低于当前 LLM 重排基线 |
| Q6 | **答案联机溯源跳转** | S4：V1.0 验收不满足 | 来源芯片带 `chunk_id` + `page`/`ts_start`，点击跳文档页或播放器 seek（播放器 seek 已有代码可复用） | 点击跳转偏差 ≤2s（产品报告 P5） |
| Q7 | **答案缓存 + 查询归一化** | 重复问法重复付费 | `归一化问题 hash → (answer, sources)`，TTL 10min，命中直返 | 命中率统计进成本看板 |

### 5.2 问答速度优化（现状 vs 目标）

**当前实测**（09 号提速后）：缓存命中检索 ~5ms，端到端默认强模型 ~18s；设 `QA_ANSWER_MODEL=deepseek-flash` 后 ~9.8s。首字节 0.01s，首字 7–11s 仍由模型主导。

| 手段 | 状态 | 预期 | 备注 |
|---|---|---|---|
| BM25 索引进程内缓存 | ✅ 已做 | 检索 CPU 省 60%+ | `rag.py:_get_index` |
| retrieve_multi 合并检索 | ✅ 已做 | 3 次建索引 → 0 | |
| 关 LLM rewrite / rerank（默认） | ✅ 已做 | 省 2 次串行 LLM（≤14s） | 开关可回退 |
| `QA_ANSWER_MODEL=deepseek-flash` | ⚠️ 开关有、**`.env` 未启用** | 18s → ~10s | **性价比最高的一步**：质量需评测集验证后再定是否常开 |
| 本地 bge-reranker 替代规则重排 | 待做 | 质量↑，耗时持平或↓ | Q5 |
| 答案缓存（Q7） | 待做 | 重复问题 → 接近 0s | |
| 流式"先出依据骨架" | ✅ UX 已做（阶段行 + 耗时计数） | 感知速度↑ | 11 号 UX 重构，18s 黑盒问题已缓解 |

**速度目标（建议）**：知识库问答端到端 P95 ≤8s（09 号标准），其中检索 ≤1s；联网/混合 ≤12s。首字节 ≤1s 已满足。**不要为了速度牺牲 Q1/Q2 的质量门**——报告明确"任一质量指标下降 >3pp 即回滚"。

### 5.3 解析（视频 / PDF / 题库）优化

| 优先级 | 动作 | 解决的报告要求 | 验收 |
|---|---|---|---|
| A1 | **字幕优先取材**：先读内嵌/外挂字幕，命中则跳过下载与 ASR | 技术报告三（一）三通道；产品报告"取材降本链"（成本降一个量级） | 有字幕视频 0 次 Whisper 调用，1 小时视频出大纲 ≤3min |
| A2 | **转写模型升级 + 学科术语纠错**：`base → small`，加载领域词表 | D9：错字进复习闭环 | 转写 quality=low 不写 ready；抽取 F1 文字 ≥0.85 |
| A3 | **OCR 并发已做，补网格拼图**：`filter_complex` 一次解码多帧 + 拼图一次调用 | 技术报告表 7 成本控制；09 号阶段 2 | 图文笔记单视频视觉调用 ≤2 次 |
| A4 | **阶段化快结果**：转写完即出大纲/文稿，图文笔记后台补齐 | 网盘式体验（09 号阶段 3） | 首份可用笔记 ≤3min，完整 ≤8min |
| A5 | **真断点续传**：按段保存 checkpoint，重试跳过已完成段 | S5："失败不吞段" | 中断后重试不重复调用模型（成本看板验证） |
| A6 | **超时按阶段 + 排队态隔离**：queued 不计看门狗，running 按阶段阈值 | D2：排队任务被误杀 | 正常长任务误判 = 0 |
| A7 | **生产栈真实跑通**（Redis 队列 + MinIO 直传 + pgvector） | V1/V2/V3、D1 | 三容器 compose 冒烟 + 20 并发不阻塞 |

> "百度网盘式 2–3 分钟"的本质（09 号已论证）：**上传秒回 + 任务可见 + 先出粗结果 + 后台补齐**。当前已做到"上传即回 + 进度可见 + 心跳防误杀 + 阶段并发"，缺的是 **A1 字幕取材（最大提速点）** 与 **A4 快结果**。这两项做完，1 小时视频≤3min 出大纲是可达的，与报告"本地 25min / 云 ASR 8min"口径并不矛盾——后者是全量图文笔记的保守上界。

## 六、接下来如何改进：路线与顺序

> 用户已确认"真实上线、先提速"。本路线在已完成的提速（09 号第十节）与 UX 重构（11 号）基础上排后续，不重复已做项。

### 阶段 1（本周，2–3 天）：把已有开关与体验变成真实收益

1. **评测集最小可用**：30 份资料 + 20 条标注问题（含 3 条诱饵/无答案），`quality_eval.py` 扩展为离线回归脚本，记录召回率/命中率/MRR/忠实度/拒答准确率/卡片可用率，绑定版本号归档。
2. **`QA_ANSWER_MODEL=deepseek-flash` 灰度启用**：用评测集对比强模型 vs flash，若六项指标下降均 ≤3pp，写入 `.env`；否则保留强模型并从别处要速度。
3. **修 D3 量纲 / S7 成本参数**：统一置信度、对齐 budget 变量、按真实单成本重设阈值。
4. **补 D11 结构化置信度**：`_kb_relevant` 直接返回 confidence，前端 `msgHtml` 用字段而非字符串匹配决定策略展示。

**出口**：评测集可跑、有第一份基线数据、问答默认 ≤10s 且质量不退化。

### 阶段 2（下周，1 周）：补质量三件套

5. **Q1 本地向量路**（sqlite-vec + bge-small-zh）与 BM25 双路融合——这是**对报告最核心欠账 T2 的最小成本兑现**，不用先迁 PostgreSQL。
6. **Q2 实体一致性校验** + **Q6 来源跳转**（chunks 与播放器两处）。
7. **Q4 chunks/notes 统一索引** + **D6 去掉 800 静默截断**（改告警）。

**出口**：双路召回有命中日志；三层幻觉治理齐备；答案可点开定位；评测集指标不降。

### 阶段 3（第 2–3 周）：视频链路兑现

8. **A1 字幕优先取材**（收益/改动比最高）→ **A2 转写升级 + low 门控** → **A3 拼图** → **A4 快结果** → **A5/A6 续传与超时**。

**出口**：有字幕的 1 小时视频出大纲 ≤3min；正常长任务误判 0；中断重试不重复计费。

### 阶段 4（第 3–4 周，上线前）：架构对齐 + 门禁

9. **生产栈真实跑通**：三容器 compose 启动，Redis + RQ + 独立 Worker、MinIO 预签名直传、pgvector。
10. **V5 账号注销/导出** + 越权黑盒用例 + 密钥扫描 + 依赖漏洞扫描。
11. **G4/G6 演练**：备份恢复（RPO 24h/RTO 4h）、灰度回滚（≤10min）；G7 ICP 备案（两至三周，与阶段 1–3 并行启动，别等最后）。

**出口**：10 号计划的 Go/No-Go 逐域核验通过，进入灰度。

### 阶段 5（上线后 / 答辩后）：V1.5 与演进

12. 按报告落点做 OCR、跨资料检索、相似题推荐（语义级）、PDF/Anki 导出、知识点图谱；父子块与本地重排按技术报告第七章在评测集上验证后再进排期。

> **最容易踩的坑**：先迁 PostgreSQL 再补评测集。没有评测集就没有回滚依据，迁移过程中的质量退化无法发现，等于把 5pp 的退化上线。顺序必须是 **评测集 → 双路召回 → 架构升级**。
