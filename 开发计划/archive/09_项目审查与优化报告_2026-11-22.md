## 第二部分　流程 / 功能 / 参数 / 架构的降级点

### 2.1 报告蓝图 vs 实际实现（核心落差）

产品报告与技术报告描述的是一套"七层、可上线"的架构，实际代码是一套"单体、可演示"的实现。逐项对照：

| 维度 | 报告/设计承诺 | 实际实现 | 证据 | 影响 |
|---|---|---|---|---|
| 前端 | React 19 + Ant Design 5 + Vite | 原生单页 `index.html`（约 2010 行 / 48KB） | `frontend/index.html` | 无构建流程，可维护性差；单文件已接近上限 |
| 数据库 | PostgreSQL + pgvector + HNSW | SQLite（`DEV_MODE=true`） | `config.py:17,24`；`.env` | 无向量能力、无并发写、无生产级备份 |
| 任务队列 | Redis 队列 + 独立 Worker 进程 | 进程内 `threading.Thread` + `queue.Queue`，**单线程串行** | `worker/runner.py:51,244` | 一个长视频转写会阻塞所有后续任务；进程重启仅靠 DB 状态恢复 |
| 对象存储 | MinIO 预签名直传，字节流不进 API | `STORAGE_BACKEND=local`，同步写本地磁盘 | `config.py:19-20`；`.env` | 大文件上传占内存/带宽，与"首屏 2 秒"目标互斥 |
| 检索召回 | 向量 Top20 + BM25 Top20 双路融合 | 仅 `BM25Plus` Top5 | `services/rag.py:27-30` | 型号/编号/公式等精确匹配可用，语义召回完全缺失 |
| 重排 | 交叉编码器逐对打分，压到 3~5 条 | LLM 语义重排（`query_opt.rerank`） | `services/query_opt.py:121-154` | 每次问答多一次 LLM 调用（≤6.5s），慢且贵 |
| 父子块 | 命中后回溯 1200 字父块 | 未实现 | 技术报告三（一）自述"已设计尚未实现" | 上下文完整性不足 |
| 幻觉治理 | 强制引用 + 分数阈值 0.7 + 实体一致性拒答校验 | 强制引用 + 关键词覆盖率 0.34；**无第三层一致性校验** | `routers/qa.py:76-83`；`config.py:52` | 模型编造数值/专有名词无拦截 |
| 索引维护 | 内容哈希去重 + 增量重建 + 灰度切换 | 有内容哈希去重（`documents.py:44`），无增量/灰度 | 代码审计 | 无回滚机制 |
| 权限模型 | 租户 / 资源 / 行级 三层 | 仅 `user_id` 单层过滤 | `rag.py:20`、`documents.py` 等 | 无共享/班级场景隔离 |
| 会话 | HttpOnly Cookie + Redis 会话 | Redis 不可用时降级内存 | `security.py:71-82` | 多进程/重启丢会话，仅开发可用 |
| 传输安全 | HTTPS、Cookie Secure | `COOKIE_SECURE=false` | `config.py:62`、`.env` | 不满足 G3 上线门禁 |

### 2.2 功能模块降级点（按严重度）

**阻断级**

1. **进程内单线程 worker**：`runner.py` 用单线程消费队列。视频转写/批量解析期间，卡片生成、仪表盘生成等所有任务排队；看门狗虽能救"卡死"，但救不了"慢"。这是视频超时的结构性根因之一。
2. **同步重活曾拖死服务**：QA 报告 8.1 记录"所有功能无法执行"，根因是同步任务阻塞 uvicorn 事件循环。现已改后台任务，但仍是**进程内**单线程，未真正隔离。
3. **无 HTTPS / 无备份 / 无 CI / 无监控**：G4–G7 全部未开展，不具备上线条件。

**严重级**

4. **检索每次全量重建**：`rag.py:23-28` 每次 `retrieve()` 都 `SELECT ... LIMIT 800` 取全部块→jieba 分词→新建 `BM25Plus`。问答对 3 个改写查询各调一次（`qa.py:274-287`），即**每次问答重建 3 次全量索引**。
5. **视频 OCR 串行**：`frames.py:264-269` 逐帧 `await _ocr_one()`，12 帧 × 视觉大模型串行，无并发、无拼图批处理。
6. **转写质量无硬门控**：`base` 模型中文错字（"间隔重复"→"建格重复"）；虽有 `quality()` 标 low，但**仍写入 `ready`**，低质内容进入学习物料。
7. **联网检索为 HTML 抓取**：`websearch.py` 靠正则解析 Bing/DDG 页面，长问题被泛化；无搜索 API，质量不可控。

**一般级**

8. **判分鲁棒性**：虽已修子串匹配（R7），多选/填空边界仍需更多对抗样本。
9. **题目识别 16/22**：跨页题、纯图解答题漏识别。
10. **会话/成本护栏形同虚设**：`DAILY_COST_LIMIT_CNY=250` 远超实际单次成本（¥0.003），基本不会触发（`config.py:49`）。

| 参数 | 当前值 | 问题 | 建议 |
|---|---|---|---|

## 第三部分　报告 vs 实现：未完成功能与联动断裂

### 3.1 上线门禁（G1–G7）达成情况

| 门禁 | 判定 | 缺口 |
|---|---|---|
| G1 功能与质量 | ⚠️ 部分 | 无评测集，解析成功率≥90%、卡片可用率≥85%、F1≥0.85 全部未量化 |
| G2 性能 | ⚠️ 部分 | 无 P95 压测，视频全链路同步占用 |
| G3 安全 | ⚠️ 部分 | 无 HTTPS、日志脱敏未验证、越权仅代码审计未做黑盒 |
| G4 可恢复 | ❌ 未做 | 无每日备份、无恢复演练 |
| G5 可观测 | ❌ 未做 | 无指标、无三条告警、无成本看板 |
| G6 发布 | ❌ 未做 | 无 CI tag/回滚演练，Docker 三容器未联调 |
| G7 合规 | ❌ 未做 | 无 ICP 备案、用户协议、隐私政策 |

### 3.2 报告承诺但未落地的能力

- **向量检索（语义召回）**：技术报告三（二）核心设计，代码完全未接。DeepSeek 无 embeddings 接口是客观原因，但本地 embedding（bge-small）方案至今未采用。
- **交叉编码器重排、父子块、索引灰度切换、行级权限、断点续传**：技术报告明确写"已设计尚未实现"或"可配置"，实际均未实现。
- **Docker 三容器联调**：`deploy/docker-compose.yml` 存在（db/redis/minio/app/nginx），但从未实跑；本地 SQLite 通过 ≠ 生产栈通过。

### 3.3 联动效果不好的地方（跨模块数据流断点）

1. **chunks 与 notes 两套检索路径未统一索引**：笔记正文参与召回是后期补丁（`_recall_notes`），与 `chunks` 表各自为政，同一知识点可能命中其一而非最优，无法统一重排。
2. **任务态与文档态一致性无保障**：看门狗 600s 固定超时，而转写进度仅在每段完成时回写（`video.py:74-75`）。长视频静默段可能超过 600s，导致**正在正常转写的任务被误判失败**，出现"任务失败但视频其实在后台完成"的联动错乱。
3. **视频时间轴与播放器未联动**：QA 报告 10.4 明确"未做点击跳转到对应播放位置，目前只高亮"；B站/抖音无代理播放，无法"边看边记"。
4. **问答策略切换靠字符串匹配**：`qa.py:520,532` 用回答里是否含"未在资料中找到依据"来决定转联网（`_REFUSAL` 列表），脆弱且不可解释，容易出现"该联网没联网 / 不该联网却联网"。
5. **仪表盘与学习计划未打通**：计划页已从导航移除但接口仍在（`05_阶段性报告` 已知问题），计划完成度未进入仪表盘统计，"今日该学什么"未真正闭环。
6. **卡片与笔记溯源单向**：`notes → to-cards` 已实现，但卡片无法反向定位到笔记/原文位置，复习时"回到出处"链路断裂。
7. **联网问答与知识问答来源混排**：`hybrid` 模式把两类 sources 简单拼接（`qa.py:265`），无统一可信度排序。

## 第四部分　检索与视频解析性能优化方案

### 4.1 问答检索为什么慢（8–19s）

实测均值 18.3s（改造前 35.1s），首字节 0.01s 但首字 7–11s。调用链分解（`routers/qa.py` → `services/query_opt.py` → `services/rag.py`）：

```
用户提问
 ├─ ① rewrite()               LLM 查询改写        ≤8s   (query_opt.py:92-97)
 ├─ ② _recall() ×3查询
 │     └─ retrieve() 每次：SELECT 800块 → jieba → 新建 BM25Plus  ← 全量重建！(rag.py:23-28)
 ├─ ③ notes 召回              另一套检索路径
 ├─ ④ rerank()                LLM 语义重排        ≤6.5s (query_opt.py:133-138)
 └─ ⑤ chat_stream()           强模型流式生成      首字 7–11s
```

**三个放大器**：① 每次问答重建 3 次全量 BM25 索引；② rewrite 与 rerank 各一次串行 LLM；③ 800 块上限随数据增长线性变慢。

### 4.2 检索优化：分层方案（含现成方案）

**L0　立即可做（不改架构，1–2 天）**

- **BM25 索引进程内缓存**：按 `(user_id, 文档版本哈希)` 缓存 `BM25Plus` 对象与分词语料，仅在文档变更时失效。当前每次重建 3 次 → 命中后 0 次，**这一步预计省 60%+ 的检索 CPU 时间**。
- **合并多次 retrieve**：`_recall` 对 3 个改写查询各检索一次 → 合并查询词一次检索，或用"原问题 + 改写词"并集一次建索引。
- **默认关闭 rewrite / rerank 的 LLM 调用**：用规则改写（`rewrite_with_domain`，零成本）兜底；rerank 用分数+覆盖率规则替代。实测质量下降有限（当前评测 8.84/10，其中重排主要解决"歌手带偏"问题，规则领域消歧已能覆盖）。
- `top_k` 由 5 降到 3（送模型的本来就只有 3~5 条）。

**L1　短期（1–2 周，引入现成组件）**

- **SQLite FTS5 替代内存 BM25**（现成、零额外服务）：SQLite 内置 FTS5，支持 BM25 权重与中文分词（jieba 预处理后写入），索引持久化、查询毫秒级。改造点：新增 FTS 虚表 + 同步写入钩子，替换 `rag.retrieve()`。
- **本地向量路**：`sqlite-vec`（纯 Python 可装）+ `bge-small-zh-v1.5` embedding（CPU 可跑），实现报告承诺的"向量 + 关键词"双路召回。
- **本地交叉编码器重排**：`bge-reranker-base` 替代 LLM rerank，省去 6.5s 的 LLM 往返，且更稳定。
- **查询结果缓存**：`问题归一化 hash → (answer, sources)`，TTL 10 分钟，命中直接返回（问答重复率高）。

**L2　中期（按报告规划）**

- 迁移 PostgreSQL + pgvector（HNSW），检索服务独立部署并预热索引；Chroma 只读兜底。

### 4.3 视频解析为什么超时（为什么做不到百度网盘式 2–3 分钟）

**先说清楚"百度网盘式 2–3 分钟"的本质**：它不是"2 分钟解析完 1 小时视频"，而是——
> 上传走秒传/直传（秒级）→ 立即返回任务 ID 并展示进度 → 后台异步转码/抽帧/建索引 → **先给你可看的粗结果**（缩略图、大纲），完整结果随后补齐。

用户感知快，是因为"重活不占前台 + 先出快结果 + 进度可见"。当前系统缺的正是这三件事。

**当前超时的六个根因（代码级）**

| # | 根因 | 证据 |
|---|---|---|
| 1 | worker 单线程串行，一个视频占住所有任务 | `runner.py:51,244` |
| 2 | 看门狗固定 600s，长视频转写静默段被误判超时 | `runner.py:32-47` + `video.py:74-75` 进度回写粒度 |
| 3 | 各层超时不对齐：LLM 120s / ffmpeg 1800s / 看门狗 600s / yt-dlp 20s | `config.py:44`、`video.py:32,144`、`runner.py:44` |
| 4 | OCR 串行 12 帧 × 视觉模型，无并发无拼图 | `frames.py:264-269` |
| 5 | 抽帧多次全片解码（`_probe_duration` / `has_video_stream` / 场景检测 / 等间隔兜底） | `frames.py:52-89,93-150` |
| 6 | 本地存储同步写，无预签名直传、无秒传去重（视频） | `config.py:19`、`video.py` |

**对标优化方案（分阶段落地）**

- **阶段 1　上传即返回**：上传接口只落盘 + 建任务 + 立即返回 `task_id`（当前已部分实现），前端展示"已排队，预计 X 分钟"——把"卡住"变成"可见的等待"。
- **阶段 2　后台流水线并行化**：
  - 抽音频 `ffmpeg -vn` 一次完成并复用；
  - 转写分段 + 并行（faster-whisper VAD 分段，或切换云 ASR / whisper.cpp）；
  - **OCR 改 `asyncio.gather` + `Semaphore(3~4)` 并发**，或按产品报告思路"网格拼图一次调用替代逐帧"；
  - 抽帧用 `filter_complex` 一次解码输出多帧，避免多次全片扫描。
- **阶段 3　先出快结果**：转写完成即返回摘要/大纲；关键帧图文笔记后台继续，前端分两次渲染（仿网盘"先出列表后出详情"）。
- **阶段 4　进度与超时治理**：
  - 每个子阶段（下载/抽音/转写/切片/生成/OCR）都回写心跳进度，避免看门狗误判；
  - 看门狗从"固定 600s"改为"无心跳 N 分钟"，并按任务类型设不同阈值；
  - 分层超时：抽帧 ≤3min、OCR 单帧 ≤30s、转写按视频时长动态估算。
- **阶段 5　架构升级（治本）**：
  - 用 **Redis + RQ / Dramatiq** 替换进程内队列，支持多 worker 并发 + 重启恢复；
  - 接 MinIO/COS 预签名直传 + 视频内容哈希秒传去重；
  - 前端改 SSE 进度推送（报告曾因"两核四G"否决 WebSocket，SSE 更轻量可作折中）。

### 4.4 预期收益

| 指标 | 现状 | L0/L1 后 | 阶段 5 后 |
|---|---|---|---|
| 问答端到端 P95 | 18.3s | **≤8s** | ≤5s |
