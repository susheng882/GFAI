# 28 · PDF 扫描件解析「质量 × 速度」诊断报告

> 诊断时间：2026-11-23　｜　角色：ocr-analysis 子 Agent　｜　性质：**只读诊断 + 单页对照实验**，未改任何源码/配置
> 依据：`24_Wave1集成验收报告` §3、`25_功能完成度阶段评审`、后端代码实测（`question_vision.py` / `parse.py` / `pipeline.py` / `ark.py` / `deepseek.py` / `config.py` / `chunking.py`）
> 样本：`【A3试卷版】数一李林六套卷做题本.pdf`（9.1MB / 13 页扫描件，DPI140 / JPEG q72）
> 基线：96.14s，13/13 页成功（目标 ≤90s，差 6.14s）

---

## 0. 一句话结论

**当前瓶颈不是「渲染」也不是「网络上传」，而是「每页一次大模型推理 + 强制 JSON 输出」**。
单页对照实验显示：同一页、同一图像、同一模型下，JSON 输出比纯文本输出慢 **约 5s/页（波动 4–9s）**，且公式标记数不降反微升；叠加 JSON 失败时的整页重试，这是一个「既慢又脆弱」的设计。
**推荐优先做「去 JSON 的纯文本直出 + 观测补齐 + LaTeX 分块保护」，预计把 96.14s 压到 65–75s 区间，同时质量不降（公式层面略升）。**

## 1. 现状链路与时间构成

### 1.1 调用链（实际代码路径）

```
parse_pdf_to_chunks()
  └─ PyMuPDFParser.parse() → 无文字层 → raise NoTextLayerError
  └─ asyncio.run(ocr_pdf_to_pages())
       ├─ render_pages()                    ← 串行，13 页逐页渲染为 JPEG q72
       └─ asyncio.gather([_one(page)...])    ← 13 页全提交，_ocr_sem 限流并发=2
            └─ ocr_page_text()
                 ├─ _vision_chat(OCR_TEXT_PROMPT)  ← 方舟 ark.chat（优先）/ DeepSeek（回落）
                 ├─ extract_json()                 ← 本地解析（毫秒级）
                 └─ 失败 → _vision_chat(OCR_RAW_PROMPT)  ← 再来一次完整模型调用
  └─ denoise_pages() → chunk_pages() → 写 chunks
```

### 1.2 96.14s 时间构成拆解（估算，待观测指标验证）

| 阶段 | 代码位置 | 实测/估算耗时 | 占比 | 性质 |
|---|---|---|---|---|
| PDF 打开 | `render_pages` | 0.02s | ~0% | 可忽略 |
| **逐页渲染（串行）** | `render_pages` | **~19s**（实测单页 1.41/1.44/1.50/1.51s × 13） | **~20%** | CPU，串行，可缓存 |
| base64 编码 | `_vision_chat` | <0.01s 总计 | ~0% | 可忽略 |
| JPEG 上传 | httpx | 单页 ~50–85KB，非瓶颈 | ~0% | 优化收益 <1s |
| **模型推理（首次调用）** | `ark.chat` × 13（并发 2） | **~77s**（96.14−19） | **~80%** | **主瓶颈** |
| JSON 解析/修复（本地） | `extract_json` | <0.01s | ~0% | 仅失败时触发重试 |
| **JSON 失败后的重试调用** | `_vision_chat(RAW)` | **未知**，每触发一次 +14~25s | 隐形放大器 | **无指标可观测** |

> 说明：`ark.chat` 单页实测 14.33 / 20.75 / 24.19s（波动大），而文档基线为 5.2–12s/页；两者差异来自网络/服务端波动，**相对差值（JSON vs 纯文本）比绝对值更可信**。按生产 96.14s 反推，实际有效单页约 11s（并发 2，约 7 波）。

### 1.3 单页对照实验（轻量验证，已执行）

**方法**：同一 PDF 第 3 页（内容页，含公式），DPI140 → JPEG q72（78KB），同一模型 `deepseek-v4-1-flash-261017`，`temperature=0`、`effort=low`、thinking 关闭；仅改 prompt 输出格式。未跑全量、未起服务。

| 组 | prompt | 样本 | 耗时 | 输出字符 | `$` 公式标记 | 行数 |
|---|---|---|---|---|---|---|
| A | 当前 `OCR_TEXT_PROMPT`（强制 JSON） | run1 | 24.19s | 1876 | 118 | 38 |
| A | 同上 | run2 | 20.75s | ~1900 | ~118 | ~38 |
| A | 同上 | run3 | 14.33s | ~1900 | ~118 | ~38 |
| **A 均值** | | | **19.76s** | ~1890 | **118** | 38 |
| B | 短纯文本 `SHORT`（无 JSON） | run1 | 15.55s | 1736 | **122** | 25 |
| B | 同上 | run2 | 15.27s | 1739 | **122** | 24 |
| **B 均值** | | | **15.41s** | 1737 | **122** | ~25 |

**观察与推论**：
1. **去 JSON 平均快 ~4.4s/页**（最保守 run3 对比也快 ~1s，最坏 run1 快 ~8.9s）。按 13 页 / 并发 2 ≈ 7 波，理论上节省 **~30s（保守 15–30s）**。
2. **质量未降**：公式标记 122（纯文本）≥ 118（JSON）；字符数少 ~150（约 8%），差额大概率是页眉/页脚/试卷标题——这些本来就会被 `denoise_pages` 删除，不影响知识库内容。
3. **纯文本耗时稳定（15.27/15.55s）**，JSON 波动大（14.33–24.19s）——符合「JSON 结构化输出触发服务端额外约束/重试」的推测。
4. **渲染是串行且非平凡**：1.41–1.51s/页 × 13 ≈ 19s，占基线约 20%；但它是 CPU 密集，线程化收益有限，**页级缓存才是它的正解**。

> **证据局限**：仅第 3 页、单账号、单次会话；JSON 组绝对值高于文档基线，不排除当时网络抖动。相对结论可用于决策，绝对秒数应以补齐观测后的全量数据为准。

## 2. 质量维度逐条诊断

### 2.1 总表（质量损失点 + 改进建议 + 三标注）

| # | 环节 | 当前做法 | 质量损失机制 | 改进建议 | 预期质量提升 | 速度代价 | 实现成本 |
|---|---|---|---|---|---|---|---|
| Q1 | 转录 prompt（输出格式） | 强制 `{"text":...}` JSON | JSON 转义占 token；复杂版面易输出非法 JSON → 触发语义更弱的 RAW 重试；结构对下游纯文本分块无价值 | **改为纯文本直出**（合并 `OCR_RAW_PROMPT` 与 `OCR_TEXT_PROMPT` 的覆盖要求：仍要求含表格/页眉页脚/公式） | 中（消除重试语义漂移，公式标记 +3%） | **−4~5s/页（提速）** | 低（~10 行） |
| Q2 | 分栏（A3 双栏试卷） | 无分栏提示，整页一次转录 | 模型可能左右栏交错读取，题干与选项错配；试卷常见 2 栏，风险高 | prompt 追加「若为分栏，先左栏后右栏逐栏转录」；质量档可对半栏裁切后分别 OCR | 中–高 | +0s（仅 prompt）/ +1 次渲染（裁切） | 低（prompt）/ 中（裁切） |
| Q3 | 数学公式 LaTeX | prompt 仅一句「用 LaTeX」 | 分式/根号/上下标/矩阵层级靠模型自觉；无二次校验；手写公式更易错 | **公式二次校验**：抽取所有 `$...$`，做括号/命令配平与长度异常检测，可疑页标记供人工/二次调用；质量档加「分式用 \frac、根号用 \sqrt、矩阵用 matrix」约束 | 中–高 | +0s（正则校验）/ +1 次调用（二次校验） | 低（校验）/ 中（二次调用） |
| Q4 | JPEG q72 有损压缩 | 全页 q72（47–85KB） | 细笔画、小字号上下标周围出现振铃，可能影响符号识别；实验证明 `$` 数量不降，但**符号正确性未验证** | 质量档改 q85 或公式密集页用 PNG；默认保持 q72 | 中（需抽样人工核对确认） | +1~3s/页（q85）/ +5~10s（PNG） | 低 |
| Q5 | DPI 140 | 固定 140 | A3 上 140 DPI 约 2310×1638，小字/下标像素偏少 | **分层**：默认 140 不动；质量档 180–200（需 A/B 验证）；**不要再降 DPI**（110 已证伪更慢 121.86s） | 中–高（高 DPI） | +3~6s/页（DPI200） | 低 |
| Q6 | 整页单次转录 | 1 页 = 1 次调用，max_tokens 16000 | 混合印刷体 + 手写答案 + 表格 + 分栏，模型易混淆「谁的答案对应谁」；输出 ~1900 字符远低于 16000，无截断但有语义拥挤 | 质量档按版面分区（表格/分栏/手写区）拆 2–3 次调用；并发 2 下不提速，纯换质量 | 中–高 | +1~2 次调用/页（+15~30s） | 高 |
| Q7 | 表格文字 | prompt 一句「表格文字」 | 无结构化要求，表格被压成线性文本，列对齐丢失，检索时语义错乱 | 表格专用 prompt 片段：「表格按行列转录为 Markdown 表格，保留表头」；仅对检测到表格线的页启用 | 中 | +0~1s/页 | 中 |
| Q8 | 页眉页脚 | prompt 明确要求转录 | 转录后被 `denoise_pages` 按「首尾 2 行 + 重复率 0.6」删除；若 OCR 换行位置漂移，可能漏删或误删正文首行 | 去 JSON 后差额页眉本就减少；保留 denoise；增加「去噪前后字符数」指标核对 | 低–中 | 0 | 低 |
| Q9 | JSON→纯文本重试 | 失败整页重试 RAW prompt | RAW prompt 丢失「表格/页眉页脚」的明确枚举，重试页覆盖度可能下降；且重试恰发生在最复杂的页 | 去 JSON 后该分支消失（Q1）；若保留，统一两份 prompt 的覆盖要求 | 中 | −14~25s/重试页（提速） | 低 |
| Q10 | 分块 `chunk_pages` | 按 `\n` 分段 →  packs 到 300 字、重叠 100 | **LaTeX `$...$` 可能被 300 字边界或 100 字重叠切断**，产生跨块残破公式；题干与选项也可能被拆到不同块 | **公式原子化**：`_pack` 中把 `$...$` 作为不可拆单元；OCR 来源页可临时放大 CHUNK_SIZE（如 500） | 中–高 | 0 | 中（改 chunking.py） |
| Q11 | 失败页处理 | 记 `ocr_failed_pages` 后**直接跳过** | 该页内容永久不进知识库，用户无感知（仅 stats 里有页码） | 入库前对失败页做 **1 次串行纯文本重试**（提高 max_tokens），仍失败才跳过并前端提示 | 高（对受影响文档） | +15~25s/失败页 | 中 |
| Q12 | 模型回落 | 方舟失败 → DeepSeek 视觉（34.7s/页） | 回落模型识别质量与方舟不同，且极慢；无指标区分 | 记录 `ocr_model_used` / `ocr_fallback_pages`，质量追溯用；回落仅在方舟真失败时触发（现状已是） | 低（可观测性） | 0 | 低 |

### 2.2 需要重点强调的两个质量问题

1. **分栏是最大未被处理的质量风险**：样本是 A3 试卷做题本，双栏 + 手写答案是典型版面。当前 prompt 只说「保持原有顺序与换行」，没有任何分栏语义，模型对左右栏的阅读顺序无法保证。**这是比 JPEG 压缩更值得优先处理的质量点**，且改 prompt 几乎零成本。
2. **分块会二次破坏公式**：即使 OCR 完美输出了 `$...$`，`chunking._pack` 按 300 字硬切 + 100 字重叠，可能把公式对拆到两个 chunk。检索/卡片看到的将是断句残式，用户会认为「OCR 把公式弄丢了」，实际是分块的锅。**这项改动零速度代价、中等实现成本，性价比很高。**

## 3. 速度维度逐条诊断

### 3.1 最大可压缩点排序

| 优先级 | 可压缩点 | 依据 | 预期节省秒数（13 页口径） | 质量风险 | 实现成本 |
|---|---|---|---|---|---|
| **P0** | **去 JSON → 纯文本直出** | 单页实验：JSON 19.76s vs 纯文本 15.41s | **15–30s**（7 波 × 4.4s）；若叠加消除 JSON 重试，保守 ~30s | 低（公式标记 +3%，字符 −8% 多为页眉页脚） | **低** |
| **P1** | **页级结果缓存** | 渲染 19s 串行 + 全部模型调用可复用；同一文档重复解析常见 | 命中时 **节省 ~96s**（全链路）；未命中 0 | 无（键含 dpi/模型/prompt 版本，失效即重算） | 中（需缓存存储与 key 设计） |
| P2 | JSON 失败重试的消除/收敛 | 重试 = 额外一次 14–25s 调用；无指标，次数未知 | 每消除 1 次省 14–25s | 低（去 JSON 后自然消失） | 低（依赖 P0） |
| P3 | 渲染阶段并行化 | PyMuPDF `get_pixmap` 可能释放 GIL | 理论上 ≤19s，实际可能仅省 3–8s | 无 | 中（ThreadPoolExecutor，收益不确定） |
| P4 | 空白页/纯色页本地预筛跳过 | 需先本地检测；本样本大概率无空白页 | 本样本 ~0s；通用场景按跳过页数计 | 低（阈值需保守） | 中 |
| P5 | 方舟 economy 模型对照 | 当前已是 `deepseek-v4-1-flash`；55 模型中仅 4 个开通，可用 economy 未查证 | 未知（可能 −2~5s/页） | 中（识别质量可能下降） | 中（需先查 `/models` 与视觉能力） |
| P6 | 并发 2 → 3 边界实验 | 文档明确：3 并发即 429 且排队 171s | 理论 ~30s，但**已证伪** | 无 | 低（但不建议做，见 §5） |
| P7 | 图像二值化 / 降采样到 q60 | JPEG 已仅 50–85KB，上传非瓶颈 | **<1s** | 中（细笔画损失） | 低 |
| P8 | 缩短 prompt 文本本身 | prompt ~110 字，token 占比极小 | <0.5s | 低 | 低 |

### 3.2 推荐的第一刀：为什么是「去 JSON」而不是「调并发/调 DPI」

- 调并发：**硬约束**（账号 2 并发上限），动就 429，收益为负。
- 调 DPI：110 已试且**更慢**（121.86s），升 DPI 增加渲染与传输，方向相反。
- 去 JSON：**同时**缩短输出 token、消除服务端 JSON 约束开销、消灭重试分支，且改动局限在 `ocr_page_text` 一个函数，**下游零改动**（`chunk_pages` 本来吃纯文本）。是唯一同时满足「收益确定 + 风险低 + 成本低」的改动。

## 4. 质量与速度的权衡建议

### 4.1 推荐组合：「默认均衡（质量优先底色）+ 快速模式可切换」

| 维度 | **默认 `balanced`（推荐）** | **`quality` 质量档** | **`fast` 快速档** |
|---|---|---|---|
| 输出格式 | **纯文本直出（无 JSON）** | 纯文本直出 | 纯文本直出 + 最短 prompt |
| DPI | 140（不动） | 180–200（需 A/B） | 140（110 已证伪更慢） |
| JPEG 质量 | q72 | q85 / PNG | q60 |
| prompt | 纯文本 + 分栏提示 + 表格/公式约束 | 追加 `\frac`/`\sqrt`/矩阵约束 + 分区转录 | 最短：仅「逐字转录 + 公式 LaTeX」 |
| 并发 | 2 | 2 | 2 |
| max_tokens | 16000（保持，实测远未触顶） | 16000 | 12000 |
| 公式二次校验 | 开（正则配平，0 延迟） | 开 + 可疑页二次调用 | 仅正则 |
| 失败页串行重试 | 1 次 | 1 次（高 max_tokens） | 0 次 |
| 页级缓存 | 开 | 开 | 开 |
| 预估耗时 | **65–75s** | 90–120s（质量换时间） | 55–65s |

**决策理由**：默认档拿走「去 JSON」这个几乎无质量代价的速度收益，把省下的时间预算反哺给「分栏 prompt」「公式配平校验」「失败页重试」这些质量项，整体质量与速度同时改善；质量/快速两档只在同一组旋钮上取值，不引入第二套链路。

### 4.2 配置项暴露方案（新增 / 调整）

| 配置项 | 默认值 | 含义 |
|---|---|---|
| `OCR_PROFILE` | `balanced` | `quality` / `balanced` / `fast`；作为上面一组旋钮的预设，单环境变量切换 |
| `OCR_OUTPUT_FORMAT` | `plain` | `plain`（推荐）/ `json`（兼容旧行为、便于回归对照）；**默认改 plain 是本次核心改动** |
| `OCR_JPEG_QUALITY` | `72` | JPEG 传输质量；quality 档建议 85 |
| `OCR_COLUMN_AWARE` | `1` | 是否在 prompt 注入「分栏先左后右」提示；几乎零成本，默认开 |
| `OCR_FORMULA_CHECK` | `1` | 是否对 `$...$` 做配平/长度异常检测并记入 stats |
| `OCR_CACHE_ENABLED` | `1` | 页级结果缓存（key = 内容 hash + 页码 + dpi + 模型 + prompt 版本 + profile） |
| `OCR_FAILED_PAGE_RETRY` | `1` | 失败页是否做 1 次串行纯文本重试 |
| `OCR_MAX_CONCURRENCY` | `2` | **保持不变**（账号硬约束，勿上调） |
| `OCR_DPI` | `140` | **保持不变**（110 已证伪更慢；quality 档才上调） |
| `OCR_OBSERVABILITY` | `1` | 是否采集 §6 的每页指标到 stats |

> 现有 `OCR_ENABLED` / `OCR_DPI` / `OCR_MAX_TOKENS` / `OCR_MAX_CONCURRENCY` 四个变量继续兼容，不破坏既有部署。

## 5. 不做什么（低投入产出比 / 已证伪）

| 不做项 | 理由 |
|---|---|
| **降 DPI 提速（如 110）** | 已实测 **121.86s > 96.14s**，方向反了；不要重复试验 |
| **PNG / DeepSeek 视觉通道** | PNG+DeepSeek 34.7s/页（>400s），PNG+方舟 9.5–17.5s/页，均劣于 JPEG q72+方舟 |
| **本地 PaddleOCR / 自建 OCR 部署** | 模型下载 + GPU/CPU 部署 + 中文数学公式→LaTeX 后处理，成本远高于改 10 行 prompt；且本次仅差 6.14s，不值得引入新依赖与运维负担 |
| **并发 2 → 3** | 文档明确该账号 3 并发即 429，且排队 171s 才返回；收益为负，除非换账号/申请提额，否则不碰 |
| **图像二值化 / q60 降采样作为主手段** | 单页 JPEG 仅 50–85KB，上传不是瓶颈；实测节省 <1s，却带来细笔画质量风险 |
| **纯靠「缩短 prompt 文本」提速** | prompt 仅约 110 字，token 占比极小，收益 <0.5s；真正的开销在「输出 JSON 结构」，不在输入 prompt 长度 |
| **盲目引入 mineru 替换整条 OCR** | mineru 是另一套重型管线（600s timeout），与「同构 pages → chunk_pages」链路不兼容，改造面大；仅作为离线质量对照可选，不进默认链路 |
| **换 economy 模型作为确定方案** | 当前 `deepseek-v4-1-flash` 已是 flash 档；55 模型中仅 4 个开通，哪个支持视觉且更 economy **未查证**。列为待验证实验，不直接落地 |

### 6.1 当前已有（`stats` 回传 `task.result`）

`parse_mode`、`ocr_pages_total`、`ocr_pages_ok`、`ocr_failed_pages`

### 6.2 建议补充（按优先级）

| 指标名 | 类型 | 计算方式 | 能回答什么问题 |
|---|---|---|---|
| `ocr_page_chars` | `int[]` | 每页 `len(text)` | 哪页疑似空白/封面/识别不足（字符数异常低）；定位质量洼地 |
| `ocr_page_formula_count` | `int[]` | 每页 `text.count('$')//2` | 公式是否被吞；与「渲染墨迹密度」对照可发现公式丢失 |
| `ocr_json_retry_pages` | `int[]` | 触发 RAW 重试的页码 | **JSON 脆弱度**：多少页、哪些页重试；直接量化 P0/P2 的收益 |
| `ocr_model_used` / `ocr_fallback_pages` | `str` / `int[]` | 每次调用记录实际模型 | 是否回落到 DeepSeek（34.7s/页），质量差异可追溯 |
| `ocr_page_seconds` | `float[]` | 每页 `ocr_page_text` 耗时 | 找慢离群页；验证「JSON vs 纯文本」的线上收益 |
| `ocr_render_seconds` | `float` | `render_pages` 整体耗时 | 量化 §1.2 的 19s 渲染占比，决定是否做缓存/并行 |
| `ocr_completion_tokens` | `int` | 累加各页 `res.completion_tokens`（当前 `LLMResult` 已带该字段但未用） | 成本/速度信号；识别是否接近 `OCR_MAX_TOKENS=16000` 截断 |
| `ocr_truncated_pages` | `int[]` | `completion_tokens >= 0.95*max_tokens` 的页 | 防止「输出被截断却当成功入库」 |
| `ocr_chunks_after` | `int` | `chunk_pages` 后的块数 | 关联 OCR 文本与下游检索规模；发现分块爆炸/塌缩 |
| `ocr_formula_broken_chunks` | `int` | 分块后统计奇数 `$` 的块数 | **直接暴露 Q10（分块切断公式）**，零推理成本 |

## 7. 结论

### 改了哪些文件

- **仅新建** `开发计划/28_PDF扫描解析质量速度诊断.md`（本文件）。
- 未修改任何源码、配置、`.env`；未启动 8011/8012 服务；未跑 `verify_all`；未跑全量 13 页；未 git 提交。
- 单页实验仅通过 `python -` 从 stdin 执行内联脚本，未落盘任何 `.py` 文件。

### 核心结论（5 条以内）

1. **主瓶颈是「每页大模型推理 + 强制 JSON」**，占基线约 80%；渲染串行占约 20%；base64/上传/本地 JSON 解析可忽略。
2. **去 JSON 改纯文本直出是唯一「提速 + 不降质 + 低成本」的三赢改动**：单页实测快 ~4.4s/页、公式标记 122≥118，预计全量 96.14s → 65–75s。
3. **两个被低估的质量风险**：A3 分栏无语义（题干/选项错配）、`chunk_pages` 按 300 字硬切可能切断 `$...$` 公式；两者改善成本都低，优先级高于 JPEG/DPI 微调。
4. **已证伪路径不要重试**：DPI 110 更慢（121.86s）、并发 3 即 429、PNG/DeepSeek 更慢、本地 PaddleOCR 投入产出比低。
5. **先补可观测性再谈达标**：当前 stats 无法回答「JSON 重试了几次、哪页公式丢了、哪页慢」；建议至少补 4 项每页指标，用数据验证优化收益。

### 未查证项（含未验证的假设）

- 本样本 13 页中**究竟有几页触发了 JSON→纯文本重试**——无指标，无法从现有数据得出；这是 §1.2 中「隐形放大器」的最大不确定项。
- JSON 输出与纯文本输出的**符号级正确性**（分式层级、上下标、根号、矩阵）未做人工逐字符核对；实验只用 `$` 数量与字符数作代理指标。若追求严格质量结论，需抽样 2–3 页人工比对原图。
- **方舟可用 economy 模型清单**及其视觉能力未查证（需查 `/models` 与逐模型探活）；当前账号仅 4 个模型开通。
- **DPI 200 / q85 的质量收益**未做 A/B；高 DPI 是否真正提升公式识别、提升多少，尚未验证，故在质量档中标注「需 A/B」。
- **页级缓存命中率与键设计**（内容 hash / 页码 / 模型 / prompt 版本）未做数据结构与存储选型验证。
- 单页实验的 JSON 组绝对值（14–24s）高于文档基线（5.2–12s），差异可能来自网络抖动或服务端状态；**相对差值方向可信，绝对秒数需以补齐观测后的全量数据为准**。
- 手写答案的识别质量未单独评估：当前 prompt 未区分「印刷题干」与「手写答案」，二者混在同一转录文本中，是否影响后续卡片生成未验证。
