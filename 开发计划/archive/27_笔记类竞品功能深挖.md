## 7. 两个重点短板深挖

### 7.1 笔记↔卡片同源：需要什么数据结构改造

**现状与断点**（基于只读代码 + 25 号，精确表结构**未查证**）：

```
notes(id, title, content=整段 Markdown 字符串, summary, folder_id, source)
        │  POST /notes/:id/to-cards（一次性 AI 派生）
        ▼
cards(id, ... , mastery, due ...)   ← 独立表，存自己的问题/答案副本
```

三个断点：① 改笔记不会回写卡片；② 复习卡片看不到周边上下文；③ 卡片没有指回笔记中具体位置的锚点。这正是 22 号 §2.5 标注的「GFLC 现状是断点」。

**竞品做法**：RemNote 把每条 bullet（Rem）当作卡片源，正文里 `正面 == 背面` 就地成卡；Logseq 给块加 `#card`、子块为答案。共同点是**卡片是笔记块的派生视图，不是独立副本**。

**方案 A：全量块模型（RemNote 式，高成本，3–5 人日）**
把 `notes.content` 从整段字符串升级为 `blocks` 表：

| 新增/变更 | 字段建议（GFLC 自定，不照抄竞品字段名） |
|---|---|
| `note_blocks` | `id`、`note_id`、`parent_id`、`sort_order`、`type`（text/heading/todo）、`content`、`anchor`（GFLC 块锚）、`content_version` |
| `cards` 增列 | `source_block_id`（→ `note_blocks.id`）、`source_version`、`synced_at`、`is_derived`（旧卡=0） |
| 新增关联 | `note_block_cards(block_id, card_id, front_expr, back_expr)`，直接存 `::` 切分后的正反面片段或表达式 |
| 编辑器 | `<textarea>` 换成块编辑器：Enter 建块 / Tab 缩进 / 拖拽 / 行内 `::` 识别与预览（这部分是主要成本） |
| 迁移 | 旧 `cards` 保留为 `is_derived=0` 独立卡；旧 `content` 按空行/标题切块回填，切不准的整篇作一块 |
| 一致性 | 块 `content_version` 变化 → 标记关联卡「待更新」，提供「一键同步卡片」而非静默覆盖（用户可控） |

**方案 B：轻量锚点（推荐先落地，中成本）**
保留 `notes.content` 为 Markdown 字符串，只加约定：正文写 `正面 :: 背面`，保存时按行解析出「成卡行」并写入 `card_anchors(note_id, line_no, anchor_id, front, back, hash)`；`cards` 增 `source_note_id` / `anchor_id` / `hash`。复习时正面/背面**从当前正文实时读取**（或带 hash 校验的缓存），hash 不一致提示「源笔记已改，点此同步」。先不做块编辑器，避免编辑器重写风险。

**落地顺序建议**：B 的数据结构 → B 的行内语法与预览 → 块锚稳定化 → 再评估是否上 A 的块编辑器。无论哪个方案，`::` 是 GFLC 自定语法，**不抄 `==`/`>>`**；验收点 = 「改笔记正文后对应卡片正反面随之变化」「复习页能看到来源笔记标题与上下文」「旧卡片不丢失」。

### 7.2 vault 本地文件化：竞品体验怎么做，我们前端该怎么补

**竞品体验要点**（查证）：
- Obsidian：vault = 本地文件夹，首次启动二选一「新建空 vault / 打开已有文件夹」，可按项目建多个 vault；磁盘里的 `.md` 文件就是笔记，文件树即目录，外部工具可 grep/git；同步靠第三方文件同步或官方 E2EE。
- Logseq：graph = 本地 Markdown/Org 文件，强调 *"Plain-Text Ownership / git-friendly"*；同步同样交给第三方或付费 E2EE。
- **共同心智**：用户先选一个本地目录 → 应用立刻展示该目录里的笔记文件树 → 改动以文件为单位可见、可版本管理；同步是「显式、可观察」的，不是隐含的云服务。

**我们现状**：后端 `/notes/vault` GET/PUT/export + 增量同步**已完整**；前端无入口、默认未启用（25 号 §2.3 标 ⚠️，§4 列 P1，预估 0.5 人日）。

**必须说清的 Web 边界**：竞品是桌面应用可直接读任意本地目录；我们是 Web 应用。浏览器**不能默认读写任意本地目录**，只有 File System Access API（Chromium 系）可经用户授权选目录；否则只能退化为「上传/下载文件夹 + 显式同步」。若走 Tauri 桌面壳（25 号 P3，需用户确认）才获得完整目录权限。**报告不声称 Web 端能做到桌面级无缝目录挂载。**

**建议前端落点（低成本）**：
1. 设置页新增「本地文件库」卡片：一句说明 + 启用开关 + 「选择本地目录」/「立即同步」/「导出」三动作；状态行显示「已连接目录 / 上次同步时间 / 待同步变更数」。
2. 笔记页左栏顶部加一条 vault 状态条：`本地库未启用 · 连接目录`；启用后显示变更数，点「同步」触发已就绪的 GET/PUT。
3. 交互语义做成**显式同步**（与后端增量同步契约一致），不要伪装成实时双向；冲突时给「保留本地 / 保留云端」二选一，不静默覆盖。
4. 验收点：能在未启用/已启用/有待同步变更/同步失败四态间切换且不报错；导出能下载；默认态不影响现有笔记主流程。

### 核心结论（5 条以内）
1. **最高性价比的是 vault 前端入口**：后端 GET/PUT/export + 增量同步已就绪，前端补「设置页卡片 + 笔记页状态条 + 显式同步」即可落地（P0，低，无模型改造）。
2. **同源行内成卡是最大断点**：`to-cards` 一次性派生使笔记与卡片双份维护；建议先走「`::` 行内语法 + 锚点表 + hash 校验」的轻量方案 B，再评估全量块模型，避免直接重写编辑器。
3. **块级引用是第二个结构性缺口**：Obsidian/Logseq 都把粒度降到块并让源变同步；我们需在 Markdown 渲染之外引入稳定块 ID，才能让反链、大纲定位、同源卡片共用一套底座。
4. **三类骨架不用重画**：三栏笔记页保持现状只补宽度/命名布局；数据库多视图与查询视图列 P2，先留切换位；大纲编辑先做「点击定位」子集，不急着上块编辑器。
5. **AI 与模板是低成本快赢**：飞书式文档级速览摘要、Obsidian/Notion 式笔记模板、飞书式章节总结跳转，均可基于现有 `ai-suggest` 与右栏大纲增量实现，不动数据模型。
