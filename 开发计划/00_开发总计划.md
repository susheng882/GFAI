# GFLC 开发总计划（v1）

> 编制日期：2026-11-21
> 目标：把《产品报告》《技术报告》定义的 GFLC，落成一个**可运行、可演示、可上线**的 MVP。
> 原则：**先闭环、后增强；结构化优先；成本前置；可演示；范围克制**（与产品报告第八章理念一致）。
> 说明：本文是「怎么把项目做出来」的执行计划，规格以 `开发提示词/01_系统提示词.md` 为准。

---

## 一、范围与验收

- **周期**：16 周（单人，每周 5 个有效工作日；55 人日 ≈ 11 周开发 + 缓冲联调）。
- **交付范围**：38 项功能中的 **27 项主线**；V1.5（8 项）与规划池（3 项）不占主线。
- **四条主路径（验收主线）**：
  1. 上传 → 解析 → 卡片 → 复习
  2. 视频 → 笔记 → 卡片
  3. 组卷 → 错题 → 回炉
  4. 问答 → 溯源跳转
- **MVP 通过标准**：四条主路径端到端跑通；解析成功率 ≥ 90%；卡片可用率 ≥ 85%；50 页 PDF P95 ≤ 60 秒；单次成本在预算区间；G1–G7 门禁通过。

## 二、开源选型（二开 + 复用）

| 模块 | 选型 | 许可证 | 结论 |
|---|---|---|---|
| **视频链路基座** | **BiliNote**（7.2k★，FastAPI + React 19 + Vite + Whisper + FFmpeg） | MIT | **二开**。技术栈与本项目高度一致，取材链/转写/截图/时间戳/Markdown/RAG 问答可直接沿用 |
| PDF 解析 | **MinerU**（80k★，上海 AI Lab；CPU pipeline / GPU vlm 双模式） | Apache-2.0（超 1 亿 MAU 或 2000 万美元月收入需商用许可） | **主用**（质量优先）。中文、表格、公式最强，最贴合备考资料；无 GPU 用 pipeline 模式。**2C4G 云服务器部署时回落 PyMuPDF**（见下） |
| PDF 轻量兜底 | **PyMuPDF** | AGPL-3.0 | 数字原生 PDF 文本层最快最省；本地开发/小内存服务器兜底。毕设非商用可用，未来商业化需复核 |
| 语音转写 | **faster-whisper** | MIT | 直接用。BiliNote 已内置，CPU int8 可跑 |
| 间隔复习算法 | **py-fsrs**（FSRS-6，Anki 23.10+ 内置） | MIT | 直接用，替代自研 SM-2；自带优化器可从复习记录反解参数 |
| 向量检索 | **PostgreSQL + pgvector** | PostgreSQL License | 直接用。同库同事务，最省运维 |
| 对象存储 | **MinIO** | AGPL-3.0 | 直接用（自部署）；预签名直传 |
| 队列 | **Redis**（或 Valkey） | RSAL/SSPL（Redis 7.4+）/ BSD（Valkey） | 直接用；自部署无影响 |
| 大模型 | OpenAI 兼容 API（通义 qwen / DeepSeek） | 商用 | 三档路由 |
| 整体参考（不二开） | Open Notebook（38.6k, MIT）、SurfSense（16.1k, Apache-2.0） | — | **只借鉴**多来源组织与引用展示，不引入其重型架构 |

> 为什么选 BiliNote 而不是 Open Notebook / SurfSense：后两者是「文档问答/研究助手」，**没有视频取材、没有学习闭环**；BiliNote 的「视频 → 转写 → 结构化笔记」正是本项目主路径②，二开收益最大。而 PDF/题库/卡片/计划/复习这些 BiliNote 没有的，正好按本项目技术方案自研补齐。

## 四、架构落地（对齐技术方案七层 + 三容器）

```
浏览器(React19+AntD5+Vite)
   │ HTTPS / HttpOnly Cookie
   ▼
[nginx 容器]  TLS / 静态分发 / 限流
   ▼
[app 容器]  FastAPI(API) ── Redis 队列 ──► Worker(转写/解析/生成)
   │                                          │
   ▼                                          ▼
[data 容器] PostgreSQL+pgvector  |  MinIO(第二块盘)
```
- API 与 Worker **同镜像分进程**；重活不进 API。
- 会话/队列/配额在 Redis（256MB 上限）；原文件与产物在 MinIO。
- 三档模型经 `app/ai/` 适配器封装，换供应商只改配置。

## 九、已确认决策（2026-11-21）

| 决策 | 结论 |
|---|---|
| 基座 | **BiliNote 二开**（视频链路复用，PDF/题库/学习闭环自研） |
| PDF 解析 | **MinerU 为主**（质量优先），**PyMuPDF 兜底**（本地/小内存服务器）；二者走同一 `ParserAdapter` 接口，按配置切换 |
| 运行环境 | **本地 Windows 开发**（Docker Desktop），答辩前再上云 |
| 大模型 | **DeepSeek API**：轻档 `deepseek-chat`、中档 `deepseek-chat`（长上下文/较高温度）、强档 `deepseek-reasoner`（R1），经 `app/ai/router.py` 三档路由 |

**DeepSeek 三档映射（落地口径）**
| 档位 | 模型 | 用于 |
|---|---|---|
| 轻档 | `deepseek-chat` | 卡片生成、日记润色、切片辅助 |
| 中档 | `deepseek-chat`（limit 输出、低温度） | 视频摘要、笔记生成、计划生成 |
| 强档 | `deepseek-reasoner` | 题目解析（五段）、自由问答（带引用） |

> 说明：DeepSeek V3/V3.2 的 `deepseek-chat` 同时承担轻/中档，用温度、max_tokens、是否分块来区分成本；强档用 `deepseek-reasoner`。若后续接入通义，只需在 `router.py` 改映射表。

7. 跑通「上传 → 解析 → 卡片 → 查询状态」最小闭环，再进 P1
